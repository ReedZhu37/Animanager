# Animanager 动画与道具存储规划

版本：0.1 · 日期：2026-11-14 · 状态：总体规划，Nodachi 首期已实施

实施记录：Nodachi 首期已落实独立轨道、共享预设、握持和接触元数据，当前格式与边界见 [独立轨道说明](MOTION_STORAGE.md)。本文的完整版本管理、迁移、搬迁包与重定向设计仍是后续规划。

本方案将动画保存为独立资产：共享固定的人体预设，分别保存人体运动、道具运动与绑定配置。素材包中的额外武器骨骼不再扩充人体预览骨架。源骨架和源轨道作为自动归档的数据保留，便于重新映射，不作为需要人工维护的人物预设。

建议采用 **JSON 描述与配置 + 无 Mesh 的 GLB 动画数据 + SQLite 查询索引**。资产库目录是完整保存单位，预设角色与武器也在库内按内容去重；播放已导入的动画不依赖原始下载路径或本机 Unreal。

## 1. 当前保存方式与需要改变的部分

依据当前实现：

| 当前行为 | 对应代码 | 调整方向 |
| --- | --- | --- |
| 每条导入结果为包含预设 Mesh 的 GLB | `Tools/CueImporter/GlbWriter.cs` | 将 Mesh 提取为共享预设，动画文件仅含节点和轨道 |
| 源额外骨骼追加至 GLB 的节点、skin joints 与逆绑定矩阵 | `Tools/CueImporter/GlbWriter.cs` | 道具节点独立于人体 Skeleton 和 Skin |
| 文件及依赖计算哈希，复制至 `assets/<hash>/` | `Core/Pipeline/ImportService.cs` | 旧资产继续支持；新增由清单引用多个共享对象的动画资产 |
| SQLite 保存路径、哈希、标签、收藏等 | `Core/Storage/AssetDatabase.cs` | 新资产的可恢复元数据也写入资产描述，数据库承担查询索引 |
| 转换报告与资产 ID 对照保存在 `uasset/<job>/` | `Core/WorkspaceApi.cs` | 将来源与依赖哈希加入每个资产版本，报告仍保留 |
| FBX 导出直接读取资产文件路径 | `Core/WorkspaceApi.cs` | 新资产先组装临时导出场景，再交给现有 Blender 管线 |

Nodachi 已有 740 条动画，源 Skeleton 为 162 根骨骼，其中 `Nodachi_Weapon_R` 挂在 `hand_r` 下。737 条包含该武器轨道；其余 3 条需要明确记录“缺少动画轨道”，不能补成假想的转刀动作。现有导入与验证范围见 [Nodachi 导入测试](NODACHI_IMPORT.md)。

## 2. 保存哪些内容

| 数据 | 内容 | 共享与修改规则 |
| --- | --- | --- |
| 人体预设 | 标准骨架定义、参考姿势、角色 Mesh、Skin、材质、来源 | 一个预设版本保存一次；动画引用 ID、版本与内容哈希 |
| 道具预设 | 我们认可的武器 Mesh 或方向轴显示配置、握持坐标系 | 独立于人物；第一阶段使用方向轴即可，无须加入新模型 |
| 源骨架快照 | 源节点 ID、名字、父子关系、参考姿势、坐标转换信息 | 相同定义按哈希共享；自动生成，不显示为另一套人物 |
| 源运动快照 | 已解码的全部骨骼轨道、时刻、原轨道状态 | 不可变；包括暂未识别的辅助骨骼，不因映射失败而丢弃 |
| 人体运动 | 映射到指定标准骨架的人体轨道 | 不含 Mesh；绑定某个确定版本的目标骨架 |
| 道具运动 | 每个逻辑道具的位置、旋转、缩放轨道及参考空间 | 不含源武器 Mesh，不追加人体蒙皮骨骼 |
| 映射配置 | 骨骼对应关系、道具分类、参考空间、坐标与参考姿势校正 | 按规则族复用；版本与哈希固定，升级不会改写旧结果 |
| 展示绑定 | 人物预设、道具预设、握持校正、显示开关 | 小型 JSON；更换预设不覆盖源运动 |
| 来源与验证 | 源文件哈希、依赖、导入器版本、转换参数、能力边界、验证结果 | 随资产版本保存，便于重现与诊断 |

**源快照和标准播放数据同时保存。** 源快照用于重新分类、映射和比较；人体与道具轨道保存本次转换的明确结果，避免导入器升级后旧资产自动改变。缩略图、轨迹折线和组装后的预览 GLB 属于可删除缓存。

默认归档本次解析实际使用的 AnimSequence、Skeleton 及必要伴随文件，按内容去重；不复制整套 RAR、演示地图、角色或武器 Mesh。遇到需要其他类型依赖的格式，先报告所需依赖，再扩展支持。原文件移动后，既有播放和重新映射仍可工作；修复解析器时也能使用已归档输入。仅有旧 GLB 的迁移资产应标记来源完整度，不能冒充拥有原始 UE 数据。

## 3. 物理目录与资产单位

继续使用现有 Library 根目录与 `index.sqlite`，增加以下结构。尖括号表示实际 ID 或哈希。

```text
Library/
  index.sqlite
  assets/                            # 现有 GLB / FBX 资产，迁移期保留
  items/
    <asset-id>/
      asset.json                     # 名称、标签、收藏、当前版本指针
      revisions/
        <revision-id>.json           # 不可变的动画版本清单
  objects/
    sha256/<前两位>/<完整哈希>.<扩展名>
                                     # rig.json、motion.glb、mesh.glb、源 uasset 等
  presets/<preset-id>/<version>/preset.json
  profiles/<profile-id>/<version>/mapping.json
  reports/<job-id>/                   # 来源、逐项结果与验证报告
  jobs/                              # 沿用任务队列记录
  cache/                             # 预览组装、缩略图与轨迹缓存
  staging/<job-id>/                   # 尚未提交的数据
```

一条动画仍是资产列表中的一项，拥有稳定 `assetId`。人体和武器不会被拆成两个需要用户手动同步的资产。它们由同一份版本清单、同一条时间轴管理；无武器动画的 `props` 为空数组。

所有必需引用都使用库内相对位置或内容哈希。源包内路径用于追溯，原下载目录只允许作为可选定位提示，不参与运行。不同动画可以引用相同的人体预设、源骨架和映射配置。无 Mesh 的 GLB 为自包含动画文件，允许重复少量节点描述；这种文件内描述不是一套需要维护的角色。

## 4. 清单和轨道格式

### 4.1 资产版本清单

下例展示 Nodachi 连招的结构。ID 与对象哈希为占位符；201 个样本及约 3.3333333 秒来自已导入的连招 01。正式文件必须包含完整 SHA-256，预设与映射版本在实施时发布。

```json
{
  "schemaVersion": 1,
  "assetId": "<stable-asset-id>",
  "revisionId": "<revision-id>",
  "parentRevisionId": null,
  "kind": "motion",
  "provenance": {
    "sourceKind": "ue-anim-sequence",
    "sourceAsset": "AS_Combo_Attack_01_All_Seq",
    "sourceClosure": "sha256:<source-and-dependencies-manifest>",
    "decoder": "CUE4Parse",
    "decoderRevision": "d05e5859ad240be10c9d5c8344f5de7c072123d0",
    "localPatches": ["ue50-tagged-raw-track-v1"],
    "normalizerVersion": "<version>",
    "sourceCompleteness": "archived-inputs"
  },
  "timeline": {
    "startSeconds": 0,
    "sourceDurationSeconds": 3.3333333,
    "sourceSampleCount": 201,
    "sampleRate": { "numerator": 60, "denominator": 1 },
    "poseSemantics": "raw-source-pose"
  },
  "source": {
    "rig": "sha256:<source-rig>",
    "motion": "sha256:<source-motion-glb>"
  },
  "mapping": {
    "id": "nodachi-ue5",
    "version": "<version>",

  "props": [
    {
      "id": "primary-weapon",
      "sourceNodeId": "bone:161",
      "sourceNodeName": "Nodachi_Weapon_R",

        "propId": "primary-weapon",

        "displayScale": [1, 1, 1]
```

清单中的每个对象引用都有可查的类型、字节数和完整哈希。`sourceClosure` 列出源文件及必要依赖的对象引用、源包相对路径和引擎版本；不能只保存动画文件的哈希而漏掉决定其解释方式的 Skeleton。

来源记录还保留源 Root Motion 开关、Force Root Lock、Additive 类型以及曲线和事件的存在情况，并分别记录是否已求值。仅保存这些标记不代表执行了对应 UE 语义；当前结果继续标记为 `raw-source-pose`。

`asset.json` 保存 `schemaVersion`、`assetId`、名称、标签、收藏、导入时间、`activeRevisionId` 和用于并发更新检查的 `generation`。展示绑定保存后产生新的版本清单，但继续引用相同轨道对象。尚未保存的预览切换、相机、选中骨骼与轨迹显隐属于工作区状态，不写回动画。

### 4.2 动画数据

三个逻辑用途分别为 `source-motion.glb`、`body-motion.glb` 与 `prop-motion.glb`；物理文件名由内容哈希决定。它们只使用节点、动画、时间及 TRS 数据，不携带 `meshes`、`skins`、材质、贴图或外部资源 URI。无道具时不生成空文件。多件道具可以共享一个 GLB，通过稳定节点 ID 区分。

glTF 支持节点变换动画，时间以秒保存，旋转使用四元数；循环、附件空间和重定向语义由本方案的清单表达。基础规范依据 [Khronos glTF 2.0](https://registry.khronos.org/glTF/specs/2.0/glTF-2.0.html#animations)。

第一版约定：

- 清单保存源帧率的有理数、源时长与样本数；轨道保留各自明确时间戳，不能只靠“帧号除以默认 30 FPS”重建。示例的 60 FPS 须在导入时经源时间数据和容差校验，不能对所有近似数任意取整。
- 每个节点同时记录稳定 ID 与显示名称。源节点 ID 在源骨架快照内稳定；标准节点 ID 在预设版本内稳定。glTF `name` 不作为唯一主键，不依赖 Godot 生成的 NodePath 持久化绑定。
- 源快照为**解码并转换坐标后的运动**，不是原始 UE 文件的字节级替代。原始文件归档与转换信息共同保留；第一版只接受当前读取器已验证的普通源姿势与线性或常量轨道。
- 长度统一为米，旋转为归一化 `xyzw` 四元数。保持现有骨骼局部坐标约定，用明确的根转换节点将其放入 glTF 的右手、Y 向上场景；不在拆分时暗中改变骨骼局部轴。保存转换版本与矩阵，所有空间运算使用已转换到同一坐标约定的矩阵。
- 第一版不做有损压缩或关键帧精简。保留源关键时刻与必要的烘焙中间点；派生轨道应在源关键时刻及区间内验证，组合层级产生误差时增加采样。
- 转刀检查覆盖中间姿态和连续运动，不只检查首尾。若原数据本身在两个采样间丢失整圈运动，插值无法补回；需要更完整的源数据，不能宣称恢复了圈数。
- 缺失通道使用该源节点的参考姿势，单值通道使用常量；记录 `animated`、`constant`、`rest-fallback` 或 `unresolved` 状态。无法确定是否属于道具的轨道保留在源快照中，报告未映射，不能悄悄丢掉。
- 负比例、非均匀缩放造成不可准确表达的剪切、未知插值或缺失必要依赖应进入不支持诊断；不能通过一次 TRS 分解掩盖精度损失。

## 5. 人体骨架与道具空间

### 5.1 固定预设

人体预设由固定 `rig` 与一个或多个兼容 Mesh 组成。UE5 标准完整骨架为 161 根，当前 Simple Mesh 使用的 joints 为 89 根；两者数量可以不同，不要求把每根控制或辅助骨骼写进 Mesh 的 skin joints。

在预设制作阶段，将完整标准骨架与现有 Mesh 的绑定对应关系校验一次并固定。后续每条动画复用同一预设版本，不增加 `Nodachi_Weapon_R`，不改顶点、索引、权重或逆绑定数据。预设升级生成新版本，已有资产仍锁定旧版本；旧版本缺失时明确提示，不能自动用另一套骨架代替。

### 5.2 道具的参考空间

第一版支持刚性道具的两种空间：

| 空间 | 保存的变换 | 播放父节点 |
| --- | --- | --- |
| `skeleton-anchor` | 相对已映射人体骨骼的运动，例如右手下的转刀 | 对应标准骨骼的跟随节点 |
| `character-space` | 相对角色场景原点的完整轨迹，已经包含源根骨骼影响 | 角色场景原点，不再额外跟随手或根骨骼 |

在坐标与锚点参考轴已经对齐的条件下，手部相对轨道由 `L(t) = inverse(A_source(t)) × P_source(t)` 得到。`P_source` 必须沿源完整父子链求值，不能直接拿一个多级辅助骨骼的局部值。播放时使用 `A_target(t) × L(t) × G`，其中 `G` 为独立保存的预设道具握持校正。

第一阶段只对已验证兼容的标准人体执行这个映射；异构人体、参考轴或比例变化由明确的重定向配置处理，不把简单乘法当作通用重定向。任意 Mesh 的自动握持适配、双手 IK 修正不包含在第一阶段。

根运动保留在人体 root 轨道，不同时复制成另一个要累加的角色位移轨道。现有 Root Motion 轨迹属于分析结果。预览的原地显示等变换必须作为统一显示层应用到人体和道具，防止相对手运动或角色空间运动重复应用根位移。

未来增加分段锚点时，保存明确区间、锚点与切换校正。区间采用左闭右开，最后一段包含终点；切换前后核对角色空间变换连续性，不凭骨骼名称自动猜测换手。涉及抛掷时优先使用完整角色空间轨迹。世界空间运动需保存场景参考原点，单个人物 AnimSequence 没有的数据不能凭空补全。

带自身骨架的武器作为独立道具预设和独立 rig 扩展；其骨骼仍不进入人体 Skin。第一版保留相关源数据，但不宣称已完成柔性武器的播放映射。蓝图、Sequencer 或另一资产产生的运动也必须有实际依赖才能恢复。

## 6. 映射规则和修改行为

映射配置保存源骨架签名、目标标准骨架哈希、人体节点映射、道具根与辅助链、参考空间、校正参数、判断依据及未解决项。规则以骨架族或素材包的共同结构复用，单动画覆盖只用于实际例外。名称匹配用于提出候选，父子关系与参考姿势用于确认；不把陌生辅助骨骼一律当成武器。

| 操作 | 实际写入 | 是否重新生成轨道 |
| --- | --- | --- |
| 改名、标签、收藏 | `asset.json` 与索引 | 否 |
| 临时换预览人物、隐藏刀 | 工作区预览状态 | 否 |
| 保存预设人物或握持校正 | 新版本清单的 `presentation` | 同一兼容 rig 下无需重新生成 |
| 把武器锚点从右手改成角色空间 | 新映射快照、新道具轨道、新版本清单 | 重新计算并验证道具轨道，不能只改一个字符串 |
| 从 UE4 切到 UE5 或改变人体比例 | 新目标 rig、新映射与派生轨道 | 需要已实现的重定向能力；当前不能静默执行 |
| 更新导入器或规则 | 保留旧版本，可显式生成新版本 | 按选择重新解析或映射，验证后才切换 |
| 只显示人体 | 展示状态 | 道具数据仍保留；导出时可明确选择不包含 |

映射快照随资产引用归档。共享规则更新不会改变其他资产已经引用的快照。默认校正变更只影响当前资产；应用到整包是显式批量任务，复用现有计划、队列、取消和逐项报告。

## 7. 索引、去重与可靠保存

### 7.1 索引和身份

保留现有 `assets` 表用于旧资产，第一阶段增加独立的 `motion_assets`、`motion_revisions`、`motion_objects` 索引和相应搜索适配，避免改变依赖列顺序的旧读取代码。统一查询层返回同一种资产列表结果；旧数据 ID 保持不变。数据库升级须有版本号和可恢复备份。

稳定资产 ID、内容哈希、来源去重键分开：

- 资产 ID 表示用户管理的条目，不随换刀或生成新版本改变。
- 对象 SHA-256 对确切文件字节去重；刚写入的文件必须重读校验。JSON 序列化固定字段顺序、数字格式和编码，避免不稳定哈希。
- 来源去重键包含源动画、实际依赖及源子片段身份；不同依赖或不同片段不能仅因预览结果相同而合并。
- 派生结果键包含源快照、目标 rig、映射快照、处理版本、坐标转换与烘焙参数。重复导入同一输入跳过已有条目；规则变化形成可追踪的新版本，而非偷偷覆盖。
- 缩略图和预览场景缓存另包含人物、道具、握持配置以及播放器版本；换握持位置只使相关缓存失效。

`items` 清单是新资产元数据的持久记录，SQLite 可由它们重建。旧资产的标签与收藏目前仅在 SQLite 中，迁移前先导出到各自的资产描述，不能声称旧库已经可无损重建。

### 7.2 提交与恢复

每条动画独立提交，批量任务已完成的动画不因后续取消而撤销：

1. 在库内 `staging` 写源对象、派生轨道和待发布清单，检查时间轴、引用、哈希及转换结果。
2. 通过验证的不可变对象移入对象库；同哈希对象先验证再复用，不覆盖不同内容。
3. 发布不可变版本清单，刷新文件后原子更新 `asset.json` 的当前版本指针。使用期望 `generation` 防止并发覆盖。
4. 事务更新 SQLite 索引与任务报告。文件发布和 SQLite 不是同一个事务；提交日志用于启动时补齐“文件已发布、索引未更新”的情况。
5. 未发布的暂存项标记为中断；重新运行从已校验对象恢复。旧当前版本在新版本完成前一直可用。

清理仅处理不被任一保留版本、预设、映射、源依赖清单或进行中任务引用的对象。第一版先提供清理预览与宽限期，不自动删除旧版本或源文件。引用扫描需要递归访问依赖清单，不能仅依赖易失的计数。

## 8. 播放、导出和搬迁

播放器先加载共享人物预设，再将人体轨道按标准节点 ID 绑定，最后创建独立道具节点并绑定道具轨道。所有轨道共用一个播放时钟，暂停、定位、倒放和循环时同步求值。无 Mesh 动画 GLB 需要专门的轨道绑定层；不能假定当前 `GenerateScene` 直接产生匹配的 Skeleton3D 或 AnimationPlayer 路径。

标准化的帧求值顺序为人体姿态更新、锚点更新、道具姿态更新、诊断轨迹采样，防止快动作出现一帧延迟。人体骨骼树显示固定预设；道具节点单独列出，检查工具可把两者作为可采样目标。

| 输出 | 建议行为 |
| --- | --- |
| 仅人体 FBX / GLB | 导出标准人体骨架及所选动画，是否带预设 Mesh 由导出选项决定 |
| 人体与道具 FBX / GLB | 组装临时场景，带独立动画道具节点，可选择包含我们的预设道具 Mesh |
| 要求武器必须是 bone 的目标工具 | 导出适配器在临时文件中生成附加骨骼，记录骨架差异；不改库内人体预设 |
| 完整库备份 | 复制库内持久数据，包含预设、源归档、对象和版本清单，缓存可省略 |
| 单资产搬迁包 | 后续增加 `.animpack` ZIP，递归收集所选版本与引用对象，导入校验哈希后复用本地对象 |

FBX 只是交换产物，不作为保存映射、语义锚点和版本历史的主格式。导出前把独立轨道组装成普通目标场景动画；不能假设外部软件认识本清单。旧资产继续使用现有导出路径，新资产使用场景组装路径。非蒙皮道具节点在 Blender 和回导中的保留情况需实际测试，失败时明确报告，不能丢弃道具后仍报成功。

单资产搬迁包不包含原素材包 Mesh，也不依赖另一台电脑上相同的绝对路径；预设对象随引用闭包一并带上。若选择省略原始 UE 归档，应在清单中标记只能基于解码快照重新映射，不能重新解析原始 UE 数据。

## 9. 旧库迁移

采用渐进迁移，新格式和现有 GLB / FBX 同时可读。先对 Nodachi 的独立库验证，不在启动时批量改写全部旧数据。

1. 扫描旧资产、来源报告和可用原始输入，生成迁移计划；保留 ID、标签、收藏及原路径。
2. 有完整原始输入时，从独立解析器生成源快照与新轨道；没有时，从旧 GLB 提取轨道并标记 `legacy-glb`，保留原文件作为证据。
3. 建立来源到原资产 ID 的对应关系，发布为该条目的新存储版本，不让列表出现两份同一条动画。
4. 对比原 GLB 与新播放结果。原始数据、坐标约定或道具分类不确定的条目继续走旧路径，报告待处理原因。
5. 全部必需检查通过后，切换该条目的活动版本；保留旧 GLB 和索引快照用于回退。模型缓存和原文件清理由后续独立操作处理。

运行中断后按每条资产的提交状态恢复；重复迁移不增加重复条目。迁移不能把未知动画曲线、事件、约束等提升为“已经支持”。普通自定义 Mesh 资产仍可保留旧导入能力；本方案的标准动画预览流程只选用预设 Mesh。

## 10. 实施顺序与验收

| 阶段 | 实施内容 | 完成标准 |
| --- | --- | --- |
| 1 存储与预设 | 版本清单、对象库、固定 UE5 预设、源快照、无 Mesh GLB 读写 | 单条 Nodachi 可保存、关闭后加载；源输入目录不可用时仍能播放 |
| 2 道具拆分 | 右手与角色空间轨道、显示绑定、方向轴、同步播放 | 转刀中间运动保留；标准人体骨架与 Mesh 数据不变 |
| 3 App 与 Console | 共用 Workspace API、检查、绑定保存、重建、任务报告 | GUI 与 Limbo 调用同一服务；可取消、重试、回退 |
| 4 整包与迁移 | Nodachi 740 条、旧 GLB 转换、索引恢复 | 不丢 ID、标签和收藏；重复导入不新增；缺轨道情况明确 |
| 5 导出与搬迁 | 组装 FBX / GLB、单资产包与闭包校验 | 人体和道具往返通过；另一独立库可打开，不依赖原路径 |

建议的 API 职责为 `MotionAssetStore`、`PresetRegistry`、`MotionNormalizer`、`MotionPlaybackAssembler` 与 `MotionExportAssembler`。对应改动集中在 `Core/Storage`、`Core/Pipeline`、`Core/WorkspaceApi.cs`、`Tools/CueImporter` 和预览绑定层，避免在 UI 回调中实现文件格式逻辑。

Limbo 建议新增 `motion inspect <id>`、`motion props <id>`、`motion rebuild <id>` 和绑定保存命令；这些是待实现的入口，不是当前已有命令。批量重建沿用任务计划和报告，接口先于额外 UI 布局实现。

必须验证的行为：

- **完整性：**保存、重开、复制库、重建索引后，样本、时长、绑定、标签和收藏一致；对象缺失、损坏或格式版本未知时明确报错。
- **人体稳定性：**导入不同包前后，预设骨架定义和 Mesh 的顶点、索引、权重、逆绑定矩阵哈希不变；161 根标准骨骼不会因 Nodachi 变为 162 根。
- **武器正确性：**在统一角色空间比较源完整父子链与拆分轨道。默认握持校正为单位变换时，覆盖全部源关键时刻及区间中点；转刀另外观察刀尖等偏移点轨迹，不能只看武器根位置。
- **精度：**第一版将内部转换的位置 0.0001 米、旋转 0.1 度作为初始验收目标；FBX 往返暂沿用现有 0.003 米、0.5 度阈值。这是待验证目标，未通过时定位原因或明确调整依据，不隐藏超差。
- **缺失与边界：**Nodachi 737 条武器轨道与另外 3 条分别报告；覆盖静态姿势、多级辅助链、同名节点、两个道具、快速旋转、根位移、非整数帧率及首尾采样。
- **操作一致：**换预设、改握持点、隐藏道具只改变预期配置；换锚点确实重算轨道；循环、定位和倒放没有累积漂移或一帧滞后。
- **恢复：**分别在写对象、发布版本、更新索引期间中断任务，重启后不存在引用半个文件的可用条目；重复导入与迁移结果稳定。
- **回归：**保留现有 UE4.23、UE5.0、UE5.6 样本和 FBX / Limbo 流程。无本机 Unreal 仍可完成导入、播放和库搬迁。

Nodachi 目前没有已有 UE 原生导出参考，验证应明确区分原始属性采样、旧 GLB 对照与 FBX 往返；不能将这些结果称为 UE 运行时验证。第一阶段优先交付固定 UE5 人体与刚性武器轨道，跨人体比例重定向、柔性武器、自动换手识别和复杂 UE 场景求值另行推进。
